# 工具调用冲突问题研究

> **工具调用冲突（Tool Conflict）**：对于同一问题，模型在仅提供部分工具时能够正确作答，但在提供更多工具后反而无法给出正确答案。我们将这种"工具增多、效果变差"的现象定义为工具调用冲突问题。

## 问题暴露

### 评估数据集

我们从不同工具导向维度选取了以下数据集进行评估：

| 工具导向 | 数据集 | 说明 |
|---------|--------|------|
| Code 导向 | TIRBench, ZeroBench_sub | 侧重代码生成与执行能力 |
| Search 导向 | DeepSearchQA, BrowseComp | 侧重信息检索与浏览能力 |
| Synergy（协同） | HLE | 需要多种工具协同完成 |

> **评测建议**：针对 HLE 数据集，可进一步关注以下子集的表现差异：SearchGain、CodeGain、SynergyGain。

### 评测方案

我们支持 3 类工具：Code、Search、Browse。在具体评测时，将工具按能力归为两大类——**Code** 和 **Search+Browse**，并设计三组消融实验来量化工具增益与工具冲突：

| 实验设定 | 提供的工具 |
|---------|-----------|
| Code-Only | 仅 Code |
| Search-Only | 仅 Search + Browse |
| All | Code + Search + Browse（全部工具） |

**关于评测次数**：前期由于评测速度较慢，每种设定仅运行 1 次；后续为提升评估的稳定性与准确性，每种设定平行运行 4 次，取平均准确率作为最终结果。

从结果来看，工具冲突问题依然明显：在绝大多数数据集上，**All** 设定的表现并未优于单类工具设定（Code-Only 或 Search-Only），甚至出现了下降。

尽管 Qwen3-VL 可能未经过专门的 Agent 能力适配，工具调用轮次仍然偏低，但通过对具体样例的深入分析，我们仍然总结出以下四类典型的冲突模式（Pattern）：

1. **工具选择错误**
   模型对问题理解不够深入，无法判断应使用哪种工具。典型表现为：计算类任务（如穷举有限环上的等价类）选择了搜索而非代码，感知类任务（如图像计数）选择了搜索而非视觉推理。这本质上反映的是模型元认知能力不足——不是工具不好用，而是模型不知道该用哪个。

2. **多工具环境下单工具使用深度不足**
   当同时提供多种工具时，模型分配给每种工具的"精力"下降。例如在搜索类任务中，Code+Search 设定的平均搜索次数（1.8 次）显著低于 Search-Only（3.2 次）。模型在拥有代码工具后倾向于"节省"搜索轮次，但某些问题恰恰需要更深入的多轮搜索才能获取充分信息。

3. **工具间的误差放大（Error Propagation）**
   多工具协同工作时，前一个工具引入的误差会被后续工具继承甚至放大。典型表现为：搜索获取了不完整的信息后，模型基于这些信息编写代码，代码精确地"计算"了一个基于错误前提的答案；同时代码输出的数值形式反过来增强了模型对错误答案的确信度。而单工具配置下不存在这种跨工具的误差传播链。

4. **多工具环境下更易陷入调用死循环**
   模型在一种工具失败后切换到另一种工具，随后再切回来，制造出"正在尝试新方法"的假象，实际上在原地打转，消耗了调用轮次却未取得实质进展。

> 由于 Qwen3-VL 的工具调用轮次偏低，上述模式可能尚未被充分暴露。后续切换至 Agent 能力更强的 Kimi-K2.5 进行进一步验证。

基于上述分析，我们初步判断工具调用冲突的核心原因在于**模型的规划能力不足**——模型缺乏对问题整体求解路径的前瞻性思考，导致工具选择盲目、调用深度不够、以及多工具间缺乏有效协调。为此，我们参考近期相关工作，引入了 **PreAct（Pre-planning before Action）** 策略：要求模型在每一轮推理时显式输出一份完整的多步执行计划，再执行当前步骤，以此增强模型的全局规划意识，缓解工具调用冲突问题。
> **PreAct策略的描述**：PreAct（Pre-planning before Action）是一种对传统 ReAct 范式的改进策略（参考 arXiv:2505.09970）。与 ReAct 每步仅生成当前 Thought + Action 不同，PreAct 要求模型在**每次生成时先输出一份完整的多步执行计划**，再执行计划中的当前步骤。具体而言，模型每轮输出包含：(1) **Previous Steps**——已完成步骤的摘要；(2) **Next Steps (Plan)**——剩余步骤的完整计划（含推理依据）；(3) **Action**——当前步骤的具体工具调用。每执行完一步获得 Observation 后，模型在下一轮会根据新信息**动态更新和精化剩余计划**，而非僵化执行初始方案。该策略的核心优势在于：通过显式的全局规划约束，引导模型在多工具环境下做出更合理的工具选择、避免浅尝辄止或陷入调用死循环，从而缓解工具冲突问题。

**结果分析：**

从对比来看，PreAct 的效果呈**混合态势**：Search 导向（+1.3）和数学推理（MathVista +2.8）任务有所受益，但 Code 导向任务整体偏弱（HLE-CodeGain -2.5，ZeroBench_sub -1.15）。

进一步分析工具调用行为发现，**PreAct 引入了明显的搜索偏向**：相比标准 ReAct，PreAct 在感知类任务中的搜索工具调用比例显著上升（TIRBench：12.8%→38.1%，ZeroBench：32.7%→70.4%），在计算类任务中同样上升（MathVista：45.3%→60.8%）。这种搜索偏向在感知和计算类任务中基本无用，造成了调用轮次的浪费，是 Code 导向任务下降的直接原因。

**结论**：PreAct 作为纯 prompt 层面的干预，虽在搜索类任务上展现了一定潜力，但同时引入了新的工具选择偏差，效果有限且不稳定。这提示我们仅靠推理时的规划约束不足以根本解决工具冲突问题，后续需要从训练阶段或架构层面寻求更深层的解决方案。

#### 冲突的本质：工具可用性如何改变模型的认知行为

通过对 27 个冲突案例的完整对话轨迹逐步回溯，我们发现表面上的"工具选错"只是症状，更深层的问题是：**多工具环境从根本上改变了模型的认知策略——从"自主推理"退化为"信息检索"。**

##### 核心机制：搜索工具触发了模型的"认知卸载"

单工具配置（Code-Only）下，模型面对难题时**被迫依赖自身推理能力**——它必须从题目条件出发构建推导链、设计算法、迭代验证。这种"被迫专注"恰恰是解决 HLE 难题所需的深度思考模式。

而 All 配置下，搜索工具的存在提供了一条"认知捷径"：**不需要自己想，可以先查一下。** 这导致模型将原本应该用于推理的认知资源卸载给了外部检索，具体表现为：

1. **推理深度截断**：模型在遇到不确定性时，不再继续深入推理，而是立即发起搜索。例如 CG#75（苏联编码谜题），Code-Only 配置中模型会尝试 KOI8-R、ASCII、Windows-1251 等多种编码假设并用代码逐一验证；All 配置中模型搜索 13 次后直接基于字面含义猜测答案，**从未进入编码分析的思维路径**。

2. **外部信息覆盖内部推理**：一旦搜索返回了任何"看起来相关"的结果，模型会**放弃已有的正确推理线索**转而采信外部信息。例如 CG#41（Allen-Cahn 方程），模型本可通过代码验证周期解的能量增长为 R³，但搜索到 Caffarelli-Córdoba 的经典 R^{n-1} 下界后，直接将"下界"误认为"最大值"，输出 a=2。搜索结果的"权威感"压过了模型自身的验证能力。

3. **资源不可逆消耗**：搜索调用的代价是隐性且不可逆的——每次搜索返回的网页内容占据数千 token 的上下文空间。模型无法感知这种消耗，直到上下文耗尽时才被迫停止。例如 CG#19（组合数学），20 次无果搜索后上下文已无空间做系统性枚举。

##### 转折点的共性结构

回溯所有冲突案例的对话轨迹，转折点具有统一的三段式结构：

> **不确定性触发 → 搜索发起 → 锚定/耗尽（不可逆）**

- **触发条件**：模型在推理中遇到需要判断的节点（该用什么公式？这个概念的准确定义？是否存在反例？）
- **关键转折**：All 配置选择搜索来"确认"，单工具配置被迫继续推理或用代码验证
- **不可逆性**：搜索一旦返回结果，要么锚定了错误方向（B 类），要么消耗了不可回收的上下文预算（A/C 类）

典型对比：

| Case | 不确定性触发点 | All 的选择 | Code-Only 的选择 | 结果 |
|------|-------------|-----------|----------------|------|
| CG#13 | 什么是最重要的域差异？ | 搜索 → 锚定在 IR 色调 | 从光学参数推导 → 景深 | 搜索给出方向性错误 |
| CG#66 | n=5 是否存在反例？ | 搜索"greedy algorithm counterexample" → 无果 | 穷举枚举 → 命中 | 搜索不可能找到新颖问题答案 |
| SG#63 | 分歧群的 breaks 是多少？ | 搜索 → 找到不同扩张的数据 | 手算 → 正确 | 搜索给出相似但不同问题的答案 |
| CG#1 | 哪种 Vigenère 变体对？ | 搜索"Google chatbot meena" → 无用信息 | 逐个实现尝试 → 第 4 个对 | 搜索中断了系统性试错 |

##### 为什么这本质上是一个训练问题

以上现象揭示了当前模型训练中的一个根本性缺陷：**模型没有学会"何时不该使用工具"。**

在训练数据中，搜索工具在绝大多数场景下是有益的（事实性问答、时效性信息等），因此模型学到了强烈的 search-first 先验。但 HLE 级别的难题恰恰属于搜索无法覆盖的长尾——这些问题要么是全新构造的（如算法反例、编码谜题），要么需要精确推理而非知识检索（如数学证明、物理推导），要么搜索结果与正确答案之间存在微妙差异（如不同问题的类似结论）。

模型缺乏的核心能力是 **"可搜索性判断"（Searchability Assessment）**——在发起搜索之前预估该问题通过搜索获得正确答案的概率。这种元认知能力的缺失使得模型在多工具环境下系统性地退化为"搜索优先、推理兜底"的策略，而非根据问题特征选择最优求解路径。

#### 缓解策略探讨

既然工具冲突的本质是"搜索工具的存在改变了模型的认知策略"，那么缓解方案需要从**恢复模型在多工具环境下的自主推理能力**出发，而非简单地限制工具调用次数。

##### 思路一：训练阶段——让模型学会"不调用"

当前训练数据的隐含假设是"有工具就应该用"，这导致模型形成了过强的工具依赖。缓解方向：

1. **构造"工具无益"的负样本**：在 SFT/RL 训练数据中，专门加入一类场景——模型发起了搜索但搜索结果是有害的（导致错误答案），而纯推理路径能得到正确答案。让模型学到"对某些问题，不搜索比搜索好"。具体可以从我们的冲突案例中提取：将 All 配置的错误轨迹作为负样本，Code-Only 的正确轨迹作为正样本。

2. **奖励"拒绝调用"行为**：在 RL 阶段，如果模型面对计算型问题选择直接推理/写代码而非先搜索，且最终答对了，给予额外 reward。让模型学到 search 不是 default action，而是有成本的决策。

3. **搜索结果质疑训练**：构造搜索返回"看似相关但微妙错误"结果的场景（如不同问题的答案、过时信息、Wikipedia 错误），训练模型在采信搜索结果前先做独立验证（如用代码 double-check）。这直接针对 Pattern B（锚定效应）。

##### 思路二：推理阶段——结构化的决策过程

不改变模型权重，而是通过推理时的策略约束来缓解冲突：

1. **Think-before-Act 强制推理**：在模型发起第一次工具调用之前，要求它先完成一段结构化的分析："这个问题的核心是知识检索还是逻辑推理？搜索能找到答案的概率有多高？如果搜索无果，我的 fallback 策略是什么？" 这本质上是将"可搜索性判断"从隐式的训练能力外化为显式的推理步骤。

2. **搜索结果对比验证**：当搜索返回结果后，不直接采信，而是要求模型将搜索结果与自身推理做交叉验证——"搜索结果说的是 X，但我自己推理的结果是 Y，两者有矛盾吗？如果矛盾，以哪个为准？" 这针对锚定效应的不可逆性。

3. **两阶段执行（Explore-then-Commit）**：将工具调用分为"探索阶段"和"执行阶段"。探索阶段允许 1-2 次轻量搜索来判断问题类型；执行阶段锁定一条路径（搜索链或代码链）深入执行，禁止切换。这针对工具振荡问题。

##### 思路三：系统架构——解耦工具选择与工具执行

更激进的方案是改变 Agent 架构本身：

1. **独立的路由模块**：将"决定用什么工具"和"实际执行工具调用"分离为两个阶段甚至两个模型。路由模块基于题目特征（领域、是否涉及计算、是否需要时效性信息等）做工具集的预筛选，执行模块只在筛选后的工具集内工作。这实际上是动态地将 All 配置退化为 Code-Only 或 Search-Only，在正确的场景下。

2. **并行竞争机制**：对同一问题同时启动"搜索路径"和"代码路径"独立执行（类似 Best-of-N），各自在独立的上下文中工作互不干扰，最后比较两条路径的答案置信度取优。这完全消除了工具间的相互干扰，代价是推理成本翻倍。

3. **搜索结果隔离**：将搜索结果放入独立的"参考区"而非直接注入主上下文。模型在推理时可以选择性地引用参考区的信息，但搜索内容不会占用主推理链的上下文空间。这从架构上解决了搜索的上下文消耗问题。

##### 各策略的适用性与代价

| 策略 | 针对的核心问题 | 实施难度 | 主要代价 |
|------|-------------|---------|---------|
| 负样本训练 | search-first 先验过强 | 中（需要构造数据） | 可能降低搜索型任务表现 |
| 搜索结果质疑训练 | 锚定效应 | 中 | 需要大量对抗性数据 |
| Think-before-Act | 首步选错 | 低（prompt 工程） | 增加推理 token 开销 |
| 两阶段执行 | 工具振荡 | 低 | 灵活性降低 |
| 路由模块 | 所有冲突类型 | 高（新架构） | 路由错误会直接截断能力 |
| 并行竞争 | 所有冲突类型 | 中 | 计算成本 ×2 |
| 搜索结果隔离 | 上下文耗尽 + 锚定 | 高（需要架构改动） | 模型需要学习新的引用模式 |

##### 我们的判断

短期最可行的方向是**训练侧的负样本构造 + 推理侧的 Think-before-Act**：前者从根本上削弱 search-first 先验，后者作为轻量级保险机制在推理时做一次"是否值得搜索"的判断。两者配合可以在不改变架构的前提下缓解最高频的 Pattern A（搜索替代计算）和 Pattern B（搜索锚定）问题。

中长期来看，**并行竞争机制**可能是最干净的解法——它从根本上避免了工具间的相互干扰，代价只是计算量，而计算成本会随硬件发展持续下降。
